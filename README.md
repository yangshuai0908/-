# TestPilot · 测试用例设计助手

输入需求文档，先分析并人工确认测试点，再生成**可编辑、可追溯**的测试用例。支持正常 / 异常 / 边界 / 权限场景，通过原文定位与语义复核帮助识别依据风险；生成结果仍需人工评审，不保证自动完整覆盖或全部正确。

```
需求文档 → 条款切块 → 需求分析 → 人工确认测试点 → 生成候选 → 原文与语义复核 → 保存用例 → 人工评审 / 导出
```

## 快速开始

```bash
# 1. 装依赖（根目录一次装完，npm workspaces）
npm install

# 2. 配置模型（必需）
cp .env.example .env
#    编辑 .env，填入 OPENAI_API_KEY

# 3. 启动前后端
npm run dev
#    前端 http://localhost:5173
#    后端 http://localhost:3001
```

### 关于模型配置

`.env.example` 默认给的是智谱 GLM 的配置，开箱可用。换别的服务只改三行（`OPENAI_BASE_URL` / `OPENAI_API_KEY` / `OPENAI_MODEL`），代码不用动。

有一个坑要注意：**`glm-4.5-air` 默认开启思考模式**，思考内容会占用 `max_tokens` 并明显拖慢响应。实测同样的请求，关思考 0.8 秒返回，不关则十几秒且容易因为 token 被思考吃光而截断。所以默认设了 `LLM_THINKING=disabled`。如果你需要模型做更强的推理，把它改成 `enabled` 即可。

另外智谱的 `temperature` 合法区间是 (0,1)，填 0 不会被拒绝但行为不可控，配置里统一用 0.2。

首次打开时点「载入示例需求」，仓库自带一份带接口定义、字段限制、权限规则的样例需求（`demo-data/requirement-v1.md`），另有一份变更版 `requirement-v2.md` 用于验证变更对比。

## 工作区

| 页签           | 做什么                                                                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **需求**       | 粘贴文本 / 上传 .md .txt .docx / 载入示例。切块后可逐条查看 REQ 编号与章节路径，确认切得对不对再保存                                                       |
| **用例**       | 按已确认测试点生成，SSE 推送进度，复核与保存完成后更新表格；表格内联改标题、优先级与人工结论，抽屉里编辑步骤、预期、证据和人工评审；证据徽标黄/红即代表依据存疑；一键导出 xlsx/csv |
| **变更对比**   | 选两个需求版本，确定性 diff 找出增/删/改的条款，定位受影响的已有用例，模型给出「需新增 / 需调整 / 建议废弃」                                               |
| **去重与评审** | 覆盖矩阵、重复组、遗漏清单、四项系统评分（覆盖率 / 场景完整性 / 步骤可执行性 / 预期可判定性），外加独立的人工评审面板                                      |
| **Agent 助手** | 右下角悬浮打开。用自然语言要求 Agent 查看需求、检索用例、检查覆盖、生成用例、对比版本或评审；Agent 会自主选择工具并根据执行结果继续处理                    |

Agent 使用受限的工具循环，最多连续调用 6 次工具。生成只追加用例；删除和覆盖操作不开放。评审与版本对比会保存正式报告，和对应工作区页面共用同一业务逻辑。

## 核心机制：怎么做到"不编造"

这是整个产品的重点，也是验收时最该盯的地方。

### 1. 每条用例必须带需求依

```json
"evidence": [{ "reqId": "REQ-002", "quote": "账号长度 6-20 位，仅允许字母、数字和下划线" }]
```

`reqId` 指向切块后的条款编号，`quote` 必须是该条款里的**连续原文**。prompt 里把这条写成硬性规则，违反即判定本次输出失败。

### 2. 后端做溯源校验（`server/src/validate/evidence.ts`）

不信任模型的自述，拿到 quote 后回到原文核对，输出三态：

| 状态         | 含义                                        | UI               |
| ------------ | ------------------------------------------- | ---------------- |
| `exact`      | 归一化后是原文的连续子串                    | 绿               |
| `fuzzy`      | 相似度 ≥0.55 且数值全部对得上，属于正常改写 | 黄，提示核对措辞 |
| `unverified` | 数值在原文找不到，或相似度 <0.55            | 红，写明具体原因 |

判定顺序里有一个关键设计：**数值锚点硬否决**。

先看这个例子——把「连续输错 5 次锁定 30 分钟」改成「连续输错 3 次锁定 10 分钟」，文本相似度高达 0.83，纯按相似度会判成"部分命中"放过去。但它改了最关键的阈值，必须拦下。所以校验时先把 quote 里的每个数值 token 抽出来，只要有一个不在原文的数值集合里，直接判红，理由写清楚"数值 3、10 不存在于该条款原文"。

反过来，「账号长度应为 6 至 20 位」这种正常改写相似度只有 0.82，如果阈值定太高就会被误杀。所以阈值不能一刀切，得靠数值锚点先把"改数字"和"换措辞"分开。

归一化也有个坑：**必须先统一区间符号再过滤字符**。顺序反了的话 `6-20位` 的连字符会在过滤阶段被丢掉，变成 `620位`，和 `6至20位` 永远对不上。

跑一遍自检就能看到全部判定：

```bash
cd server && npx tsx src/scripts/selftest.ts
```

### 3. 需求缺口进 assumptions，不许猜

需求没写的字段、阈值、提示文案、错误码，一律不准出现在步骤和预期里，只能进 `assumptions` 数组，在用例页顶部单独列出，提示人工确认。

样例需求里故意留了两个缺口（token 有效期"待定"、验证码重试次数未定义），跑一次生成就能看到它们出现在「需求缺口」区块，而不是被模型编成具体数值。

### 4. 变更对比同样不吃相似度的亏

`2.1 账号规则` 从 6-20 位改成 8-20 位，文本相似度 0.99，光看相似度会判成"未变"，最关键的改动反而漏掉。所以 diff 时加了和证据校验同源的数值差异检测：**数值集合变了就强制判为修改**，不管相似度多高。

## 人工评审闭环

系统自动评分只能回答「像不像一份好用例」，回答不了「业务认不认、改起来贵不贵」。所以用例上挂了一份独立的人工评审记录，**不参与系统评分、不经过模型**，全部由测试 / 业务人员填写。

**用例级**（用例表格两列可直接改，抽屉里填完整表单）

| 字段            | 取值                              | 说明                                       |
| --------------- | --------------------------------- | ------------------------------------------ |
| 有效性结论      | 待评审 / 有效 / 需修改 / 建议废弃 | 结论改回「待评审」会清掉评审时间           |
| 修改成本        | 无 / 低 / 中 / 高                 | 仅「需修改」时可填                         |
| 评审人          | 自由文本                          | 记在浏览器本地，切换用例不用重复填         |
| 批注 / 遗漏说明 | 自由文本                          | 写清「哪条预期不可判定」「哪个条款少用例」 |

修改成本按 **低 1 / 中 3 / 高 6 点**折算成「相对工作量」，用于横向比较返工规模。**这是产品自定义的评估刻度，不是工时估算，也不是从需求里推出来的规则**——和「不编造」原则是两码事，别混。

**条款级**：评审页「遗漏确认」默认折叠，点「展开条款清单」后逐条标 `未确认 / 已确认无遗漏 / 存在遗漏`，可写备注（失焦即保存）。系统算出的 gaps 只是候选，人工确认才算数。

**汇总**：评审页实时展示已评进度、有效率、四类结论分布、修改成本分布与点数、评审人分布、待处理用例清单。用例页改动后通过 `casesRevision` 信号自动刷新，不用手动切页签。汇总走 `GET /api/requirements/:rid/assessment-summary`，纯确定性计算，没跑系统评审也能看。

**导出**：xlsx/csv 末尾追加 4 列（人工评审结论 / 评审人 / 修改成本 / 评审批注），原有 12 列顺序不变，已回填过的模板不会错位；「需修改」「建议废弃」在 Excel 里标色。

数据落 `data/cases.json` 的 `assessment` 字段和 `data/gapReviews.json`；旧用例缺字段时按「待评审」兜底。评审页可一键清空重评（只清评审记录，不动用例本身）。

## 常见问题

**没配 API Key 能用吗？**
可以录入和查看需求；生成用例、版本对比建议、评审和 Agent 调用需要配置 API Key。未配置时会明确报错，不会生成假数据。

**生成很慢？**
生成按已确认测试点的分类分批，每批最多 3 个点，另有依据语义复核与必要的重试调用。用例页显示生成批次；点较多时可减少本次场景分类。

**模型不支持某些参数？**
只用了标准的 `/chat/completions`，没有依赖 `response_format`、function calling 这类扩展能力，换任何 OpenAI 兼容服务都能用。

**docx 解析失败？**
在 Word 里另存为 .md 或 .txt，或者直接粘贴纯文本。

## 生成依据与流程追溯

需求管理中先分析、核对原文并确认测试点。页面生成与 Agent 生成复用同一条链路，待确认和已排除测试点不参与生成。每条新用例保存来源测试点、分析版本和 runId；旧数据、手动新增和版本对比建议不会补造测试点关联。已关联数量只表示存在来源关系，不是准确率或完整覆盖率。

需求分析区、测试用例工具栏的「流程追溯」可查看执行记录；用例编辑抽屉可筛选该用例的生成和后续修改记录。记录保存在 data/traces.json，包括当时的需求/分析快照、实际提示词、模型配置与原始返回、原文/目标关联检查、语义复核、去重、保存结果、错误与重试。测试点修改/确认、用例内容修改、依据重校验和人工评审保留前后快照。模型密钥不入日志，也不记录模型内部思考过程。记录支持打开完整 JSON；导出用例时追加系统用例、测试点和生成追溯 ID。

重新生成仅在全部批次成功且候选通过处理后替换旧用例；失败时保留旧用例。生成期间分析或用例发生变化，会停止保存并要求刷新重试。追加生成允许保留成功批次，并明确显示部分成功与失败原因。服务重启后的未完成记录标记为中断。

追溯从功能上线后开始，旧操作无法追补。记录是本地 JSON 操作历史，随需求/项目删除一起清理；不是防篡改审计，也不证明操作者身份。语义复核仍可能误判，步骤执行成功不能等同于业务结论正确。
